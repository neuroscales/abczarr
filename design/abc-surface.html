abc surface design

Shape of the abc surface

The generic surface, settled before driver code. A store is a key→bytes map; a node is the typed array or group above it — and every backend is built exactly that way. Yes, we need a store abc; its default is synthesized over bagof-paths, so local and cloud come for free.

00

The short version

Every backend claim below was checked by running the library, per the repo rule “find out what they do — by running it.”

Two layers, and every backend agrees keep both

Store (get/set/list/delete) beneath a typed node. zarr-python and tensorstore both split it this way and both let you reach the store from the node.

A store abc — but a thin one yes

Five primitives + a capability query. The default store is synthesized over bagof-paths, so one class covers local and every fsspec/cloud scheme with no per-backend code.

Node stays lowest-common-denominator two valves

node.native reaches the raw backend object; driver.supports(cap) asks what it can do — so the shared surface never grows into the union of every backend’s features.

zarrs and zarrita are not drivers re-scope

zarrs is a Rust codec pipeline inside zarr-python; zarrita was absorbed into zarr-python 3.x. The real driver set is zarr-python + tensorstore.

03

Do we need a store abc? Yes.

The store is the one seam shared by everything downstream — every driver, every metadata-version reader, every fallback reads and writes through it. Without it, each driver re-implements local/cloud I/O (tensorstore already hand-rolls kvstore JSON; zarr-python passes raw strings) and the sync/async split is solved N times over.

The minimal store contract

Modeled on the intersection of zarr’s Store and tensorstore’s KvStore — five primitives and a capability query. Everything richer is synthesized or delegated behind supports.

get(key)             -> bytes | None          # None = missing
set(key, value)      -> None
delete(key)          -> None
exists(key)          -> bool
list(prefix="")      -> Iterator[str]
supports(capability) -> bool   # writes, listing, deletes,
                               # partial_read, partial_write

The default store is bagof-paths, not per-backend code

A Zarr key ("0/1/2", "zarr.json") is a path under the store root. So the generic store wraps a bagof-paths Path:

store primitivebagof-paths
get(key)(root / key).read_bytes() — missing → None
set(key, v)(root / key).write_bytes(v) — parents created
delete(key)(root / key).unlink()
exists(key)(root / key).exists()
list(prefix)(root / prefix).walk() → keys relative to root
One class, every backend

Because bagof-paths dispatches on URL scheme (local, s3://, gs://, az://, http://, any fsspec backend) and carries credentials via storage_options, one PathStore gives every filesystem and cloud store for free. The empty S3Store/GCSStore/AzureStore subclasses in abc/store.py today collapse into this one class plus bagof-paths’ protocol registry.

The three-tier discipline, on the store

Delegatetier 1
A native store that has the member (get_partial_values, getsize) — use it, gated behind supports.
Synthesizetier 2
list_dir = list + split on separator; clear = list + delete; whole-array read from per-chunk get.
Raisetier 3
Neither possible → one named error, UnsupportedZarrOperation — never a bare NotImplementedError.

Native stores, and async

A backend driver with its own store (zarr-python’s LocalStore/FsspecStore, tensorstore’s KvStore) uses its store when active, to keep its optimized, possibly-partial, possibly-async I/O; the abc store wraps it. PathStore is the default and the fallback; a native store is an opt-in optimization. Both satisfy the same five-method ABC. The async twin (AsyncStore over bagof-paths’ AsyncPath, including its native async cloud path) is where async earns its keep — chunk I/O is the hot, blocking, parallel boundary.

What abc/store.py needs

Today it is a half-built concrete class: close, iter_keys and bucket are referenced but never defined, and nothing is wired to real reads. Turn it into a real minimal ABC, add the AsyncStore twin, and delete the empty protocol subclasses.

04

The driver contract

A driver supplies primitives only; the abc synthesizes the rest, so a new driver is small. A driver may override a synthesized member when it can do better (tensorstore reading a whole region in one call) and declares that reach through supports.

open(store_or_path, ...)  -> ZarrNode        # sniff array vs group
metadata                  -> NodeMetadata    # typed, per version
read / write a chunk (or region)             # I/O the store can't infer
create_group / create_array
list / delete children (group)
_CAPABILITIES             -> frozenset        # what supports() reports
05

Compatibility with the proposed drivers

Checked against the real libraries. The surface loses nothing that matters; backend-specific extras stay reachable via native.

zarr-python reference driver

Store maps onto the five primitives directly; supports_* feed supports. zarr.Array/Group supply every node member. Needs the real metadata property, a real fill_value (currently a TODO), and the create_array keyword fixed. Codecs v2/v3, sharding, consolidated metadata all present — advertise via supports.

tensorstore async-capable

ts.KvStore maps on (read→get, write→set, delete_range→delete). Future-based: the sync driver calls .result(), an AsyncStore awaits. Rich indexing (oindex/vindex, transforms, labeled domains) is deliberately behind native. No group object — groups are paths; ZarrGroup.__setitem__ stays a named UnsupportedZarrOperation. The native valve is load-bearing here.

zarrs not a driver — a codec option

A Rust reimplementation of the codec pipeline that registers into zarr-python. No separate store or array API. Surface it as a codec-pipeline option on the zarr-python driver, not a peer driver. The metadata layer already describes which codecs run.

zarrita retire

The prototype that became zarr-python’s v3 implementation; the standalone package is legacy and drivers/zarrita.py is a 5-line stub that just raises and is not even registered. Drop it, and drop "zarrita" from KnownDriver.

07

Recommended sequence

Each step is small and testable; none needs a backend installed except where noted. The through-line: a narrow, synthesized abc surface; bagof-paths does the store I/O; each backend contributes primitives and reaches past the surface through native and supports.

1

Turn abc/store.py into a real ABC

Five primitives + supports, the synthesized members (list_dir, clear, getsize…), the AsyncStore twin. Delete the empty protocol subclasses; fix the dangling close/iter_keys.

2

PathStore / AsyncPathStore over bagof-paths

The default store — local + every fsspec/cloud scheme. Test with a memory path and tmp_path; the async one against bagof-paths’ in-process async backend.

3

One surface spec + test_parity.py

Lock the node and store surfaces — sync vs async, abc vs driver.

4

Re-fit the zarr-python driver

Real metadata, real fill_value, native Store wrapped as an abc store, capabilities declared. The reference — and the first green driver.

5

Re-fit the tensorstore driver

KvStore wrapped, .result() in the sync path, native for rich indexing, groups-as-paths kept.

6

Retire zarrita; record zarrs as a codec option

Drop the stub and the KnownDriver entry; note zarrs as a future codec-pipeline option on the zarr-python driver.

7

Deferred — the dependency-free fallback

A pure-Python chunk reader on top of PathStore, so a store works with no backend installed.
