Design · async & transactions

Async and transactions belong on the nodes

A Store in abczarr is mostly a path-holder — no node's chunk I/O passes through one. So the sync, async, and transaction surfaces belong on the objects users actually hold: ZarrArray and ZarrGroup. This is the plan for getting them there while leveraging each backend's native machinery.

status design — nothing built floor Python 3.8 verified against zarr 3.1.6 · tensorstore · zarrista 0.1.0 extends roadmap §4

01 The decisions

Six calls carry the plan. Two of them reverse the first sketch — noted where they do.

The surface lives on nodes, not stores

Sync / async / transactional APIs go on ZarrArray / ZarrGroup. The async + transaction scaffolding currently sits, unused, at the store layer — the wrong layer.

Two colors, one native — synthesize async-from-sync only

A driver implements its node ops once, in its native color. abczarr threads sync→async; it does not build the background-loop sync() in v1 — every real backend is already bi-colored, so it has no customer. (Reverses the first sketch's two-way symmetry.)

Transactions are first-class objects, spawned by the node

A Transaction collects operations; node.with_transaction(txn) returns a node view whose writes enlist; one transaction can span many nodes.

with_transaction = "an equivalent node whose writes enlist"

Not "rebind this handle." tensorstore rebinds an open handle; Icechunk re-opens the node on a session. Both satisfy one contract only if it's written the general way from day one.

No faked transactions

A backend without native support reports transactions NONE and with_transaction raises. No buffered node fallback — buffering arbitrary NumPy selections is not read-your-writes. (Reverses the first sketch.)

Atomicity is a (driver × store) property, decided at commit

Not a class constant: tensorstore's atomic=True succeeds on memory/ocdbt and fails at commit on the file kvstore — for even a single chunk.

02 Where it stands today

Verified against the tree and live backend probes, not memory.

FactEvidence
Nodes are sync-only. abc/array.py, group.py, node.py — no coroutines.
Async + transaction scaffolding lives at the store layer and no driver uses it. No _native_transaction override anywhere; no driver builds an AsyncStore.
The tensorstore node reads via a blocking .result() yet declares async NATIVE. drivers/tensorstore.py:158–161 — the declaration is aspirational; there is no async path.
Nodes have no link to their driver. Node __init__ takes only the backend object; available_drivers() builds a fresh stateless driver per call.
Attributes bypass every layer. attrs writes the metadata file directly (mkstemp+fsync+replace) — through neither store nor backend, so it cannot enlist in a transaction.

Why the reversal on synthesis

tensorstore futures are awaitable and block via .result(); zarr-python is async-first with a sync wrapper; zarrista ships both Array and AsyncArray. All three real backends are natively bi-colored, so sync-from-async synthesis has zero customers — building it now is building for a backend that doesn't exist.

03 The user surface

Proposed spelling, not existing API. open(…) is abczarr's façade; asynchronous=True selects the async twin. Async uses getitem/setitem methods, not [], because an assignment expression can't be awaited — zarr-python's choice.

04 The model

Color bridge — synthesize only async-from-sync

Transactions — shared core, two thin facades

A color-neutral _TransactionCore holds the native handle plus open / committed / aborted / atomic. Transaction and AsyncTransaction are thin facades over it, mirroring the node twins; as_async() / as_sync() return the other facade over the same core. The base ABC loses its abstract store property; the buffered store-view flavour moves to a StoreTransaction that stays the fallback for the path-based store only.

The view — four rules

with_transaction returns a new node (never mutates self._native); identity stays distinct; after commit/abort the view is dead (a new TransactionClosed naming the node and op); and every child derived from a view inherits the transaction — which needs a single _derive() seam on PathGroup (it builds children in four places today) before views exist, or the transaction leaks at the first __getitem__.

05 Backend compatibility

Icechunk isn't installed here; its row is reasoned from its documented writable_session / commit API.

Why the contract is "equivalent node," not "rebind"

Icechunk has no way to bind an already-open zarr.Array to a session, so its with_transaction re-opens on session.store and returns a new node. Write the contract that way from day one, or tensorstore's native.with_transaction() becomes the accidental spec.

06 The plan

A real sequence: settle the contract, prove it on one backend, widen, then defer the hard parts.

Before writing a line
  • Async-from-sync only — drop the background-loop sync() from v1.
  • No buffered node transaction — node-level transactions is NONE without native support.
  • "Equivalent node" contract so Icechunk's re-open fits; atomic_transactions answered per instance.
  • Spawn hook on the node, not the driver; add the PathGroup derivation seam.
  • Transaction = shared core + facades; base ABC loses store.
Prototype first — tensorstore only
  • TensorStoreTransaction over ts.Transaction; with_transaction returns a rebound array.
  • Multi-array atomic commit (memory/ocdbt); commit-time atomicity failure on file → clear error.
  • TransactionClosed on reuse; group children inherit the transaction.
  • AsyncTensorStoreArray with getitem/setitem awaiting futures; a parity test.
Second
  • AsyncZarrPythonArray/Group wrapping zarr.AsyncArray/AsyncGroup directly — no bridge.
  • zarr-python with_transaction raises until an Icechunk driver exists.
  • Generic thread-synthesized async twin, on a bounded executor, for any driver that ships none.
Defer
  • Background-loop sync() — build when a coroutine-only backend arrives (stricter re-entrancy guard, fork reset, atexit cleanup).
  • The Icechunk driver — design the re-open path then.
  • Transactional attrs / group-structure writes via ts.KvStore.with_transaction.
  • Timeouts on the sync surface and on commit().

07 Open questions

Timeoutstensorstore has .result(timeout=) and zarr's sync() takes one; abczarr's surface has neither. Add optional timeout= to sync I/O and commit()?
Partial failurea non-atomic multi-node commit can partially apply with no rollback — the API must say so, and that the transaction closes regardless.
Cross-loop storesa remote (fsspec) store's aiohttp session is bound to one loop; an async twin on the user's loop beside a sync facade on another is a hazard for remote backends. Guard or document.
store() on a viewan atomic dask write holds the whole array in the backend's writeback cache until commit() — refuse above a size, or warn?
