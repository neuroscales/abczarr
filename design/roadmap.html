Development roadmap

A plan for abczarr

A generic, multi-backend interface for Zarr I/O — with native OME-Zarr support and lossless, all-versions metadata. Today the tree is mid-refactor and does not import. This is the sequence that gets it from broken to a coherent, tested API without rebuilding the bagof ecosystem twice.

00

The short version

Five decisions carry the whole plan. Each is argued in full below; here is the call and the one-line why.

Replace the path layer with bagof-paths yes, now

_core/path.py is a 2,375-line reimplementation of bagof-paths that is currently broken. Its cloud surface isn't even wired up. Deleting it is the cheapest large win on the board.

Move attrs → bagof-magic yes, staged

The version lattice you hand-rolled in _core/metadata.py is bagof-magic's polymorphic. But port after the tree is stable, and verify three converter edge-cases first.

Own the format, borrow the I/O

Metadata parsing & cross-version conversion is the product. Chunk I/O, codecs and compression are the backends' job — synthesize a fallback only from primitives, otherwise raise one named error.

Sync-first surface, native-async where earned

Describe the surface once; bridge sync→thread for async drivers, await natively when the backend is async. Defer the hard direction (sync-over-async). Same shape as bagof-paths.

solid & tested exists, untested broken / blocker stub / absent
01

Where it stands today

A lot of surface area exists, but it is broad-and-shallow, and one commit left it unable to import. The value is concentrated in the metadata model; the liability is concentrated in the two large home-grown infrastructure layers.

Blocker · the tree does not import

The [WIP] metapath commit renamed the path classes (S3Path → WrappedS3Path) but abc/path.py still references the old names, and __init__.py imports everything eagerly. So every import abczarr… raises — even the passing metadata and OME tests can no longer be collected. Nothing ships until this is fixed.

Two facts drive everything that follows. 02

The two big forks

You asked both directly: replace the path code with bagof-paths, and attrs vs. bagof-magic. Here is the reasoning and the verdict on each.

A · The path layer → bagof-paths

Verdict Replace it — and do it early, in Phase 1

_core/path.py and bagof-paths solve the identical problem: one uniform, driver-pluggable, sync + async surface over pathlib, universal-pathlib and cloudpathlib, with S3/GCS/Azure/HTTP protocols and a driver registry. abczarr's version is 2,375 lines, mid-refactor, and its per-protocol cloud classes are referenced but never defined — so in practice only the local Path subset is exercised today.

Why it fits

  • bagof-paths already ships sync Path + async AsyncPath over one spec table — exactly the paired hierarchy abc/store.py needs.
  • Native-async fsspec cloud driver, per-loop session handling, credentials via storage_options — all the parts a zarr store on S3 needs.
  • The escape hatch path.wrapped preserves any backend-specific member the store needs.

Migration cost

  • Low at the call sites: _core/attributes.py and the drivers use only the vanilla Path subset.
  • Concentrated at one seam: abc/path.py / abc/store.py subclass the wrapper and use its register_subclass hooks.
  • Model StorePath's one bit of extra state (read_only) as a thin subclass or via bagof-paths' with_wrapped derivation.
Before you commit

Confirm bagof-paths exposes a subclassable Path/AsyncPath and a store-flavoured derivation hook. Its register_protocol / register_driver model is the replacement for abczarr's register_subclass; map the store subclasses onto it rather than onto pathlib inheritance.

B · attrs vs. bagof-magic

Verdict Migrate to bagof-magic — staged, after the tree is stable

This is the bigger, less reversible call, so it comes after Phases 0–3. But the direction is clear: abczarr has hand-built the two things bagof-magic exists to provide, and is maintaining ~3,000 lines of it untested.

The case for

  • Polymorphism is a direct match. register_subclass(zarr_format=2, node_type="array") dispatch is bagof-magic's polymorphic=True + on={"zarr_format":2, "node_type":"array"}. Your version lattice is its worked example.
  • Hint-driven fields are its premise. _core/auto derives converters/validators/factories from type hints; bagof-magic + the sibling bags do exactly that, maintained and tested elsewhere.
  • Options inherited via class keywords map cleanly onto the version×node-type inheritance you already express with mixins.

Risks to retire first

  • RFC-2119 markers. _core/rfc2119.py registers Required/Recommended/… annotation factories. Confirm these re-home onto bagof-factories' annotation model.
  • Specialised converters. numpy-DType coercion, JSON round-trip, and the regex dtype match (r\d+) must port to bagof-converters or ride as explicit ConvertTo callables.
  • TypedDict validation. schemas/ leans on get_validator walking TypedDicts (total/Required/closed/extra_items). Keep that surface until bagof-validators is confirmed to subsume it.
Sequencing

Migrate innermost-first: ZarrConfig → metadata base → array/codec/dtype classes → OME. Keep the @autofrozen/@autodefine names as thin shims over bagof-magic during the transition so call sites don't churn, then delete _core/auto once nothing imports it. If bagof-magic isn't ready for the DType/RFC-2119 cases, that's a reason to delay, not to keep building the home-grown engine.

03

Designing the generic "abc" API

The abstract layer is the whole point of the package, and it's the least finished. It should borrow bagof-paths' architecture wholesale: describe the surface once, keep drivers thin, and never let the common denominator hide a backend's strengths.

Consolidate to one layer

Delete the old flat _abc.py; keep the abc/ package (node, array, group, store, path). Two parallel definitions of ZarrArray is how the import break slipped in.

One surface spec, like _spec.py

Describe each node/array/group member once in a table — its kind (pure vs. I/O), how its result is wrapped, whether it has an async twin — instead of writing sixty method bodies twice. The engine reads the table.

Thin driver contract

A driver must supply only primitives: open, metadata, read/write chunk, create, list, delete. Everything richer is synthesized from those or capability-gated. That's what makes a new backend (zarrs, zarrita) a small file, not an 800-line one.

Metadata is first-class on every node

Each node exposes .metadata (the rich attrs model), .attrs (user attributes), and .native (the raw zarr.Array / ts.TensorStore). The metadata model is the neutral interchange between drivers.

Two contracts that keep the abstraction honest

escape hatch

node.native always returns the underlying backend object, as a documented, supported contract — not an accident of __getattr__ delegation. Anything the uniform surface doesn't name is still reachable, so wrapping never costs a capability.

capability query

driver.supports("sharding") / "async" / "partial-write" / "consolidated-metadata", answered from the driver class (never by touching a live resource). Callers branch on capability instead of catching exceptions.

One named error

When a member can be neither delegated nor synthesized, raise a single UnsupportedZarrOperation naming the operation and the driver — the bagof-paths UnsupportedPathOperation pattern. Never a bare NotImplementedError, never a leaked internal name.

04

Handling sync and async

The backends disagree: tensorstore is async at heart (futures with a sync .result()), zarr-python has a real async layer under its sync one, zarrs/zarrita differ again. Writing every method twice by hand is how the two surfaces drift. bagof-paths already solved this shape; copy it.

Async node, sync driver

Bridge the sync call into a worker thread — the run_in_executor approach _core/asyncutils.py already sketches. No second implementation.

Async node, async driver

Await the backend's coroutine directly through a native seam — the tensorstore/zarr-python fast path. Full concurrency, no thread hop.

Sync node, async driver

Defer. Driving a loop from sync code (the "portal") is the hard direction; bagof-paths defers it too. Ship the other three first.

  • Sync-first public surface. The consumers are numpy and dask, which are synchronous; make ZarrArray sync-primary and offer AsyncZarrArray where the backend earns it. Parity is enforced by a test that fails the moment the two signatures drift — bagof-paths' test_parity.py.
  • Async matters most at I/O boundaries — the store (already handled by bagof-paths) and chunk read/write. The metadata model stays pure-sync data; there is nothing to await in parsing.
  • Fix the loop handling on the way. asyncutils uses the deprecated get_event_loop(); move to get_running_loop() + an explicit executor as part of adopting the pattern.
05

Not disabling a backend's good features

The real danger of a lowest-common-denominator ABC: it quietly hides tensorstore's async concurrency, zarr-python's codec pipeline, sharding, partial reads, consolidated metadata. The three-tier discipline — delegate, then synthesize, then raise — is what prevents that.

Delegatetier 1
If the driver implements the member, call it and pass the rich arguments straight through. Keep chunk_grid, codecs, sharding and dtype config in the metadata model (already done) so a feature expressed there survives even when a convenience API wouldn't surface it.
Synthesizetier 2
Only from more-primitive members the driver does have: __array__/to_dask from __getitem__, a group walk from iterdir, whole-array read from chunked reads, pyramid levels from create_array+getitem. Never reach past the primitives.
Raisetier 3
When neither is possible, one UnsupportedZarrOperation — don't half-emulate compression, a sharding index, or a codec. A clear refusal beats a wrong result that looks right.

Paired with the node.native escape hatch and driver.supports(…) from §03, this gives three ways to reach a backend strength: it's in the uniform surface, or you branch on the capability, or you drop to .native. No feature is stranded by the wrapper.

06

How many fallbacks to own

The rule of thumb: own the format logic and the cross-backend glue; borrow I/O and compute; synthesize only from primitives; otherwise refuse. Here is where each responsibility lands.

ResponsibilityStanceWhy
Metadata parse / serialize / cross-version convertownBackend-independent spec logic — the package's core value. No backend does all versions losslessly.
Chunk / shard auto-sizing, pyramid downsampling, chunk mathownPure numeric logic already in _core/sharding.py & pyramid.py; independent of any driver.
Path & store abstraction, protocol selection, credentialsdelegate to bagof-pathsSolved once already in the org. Don't own a second copy.
to_dask, __array__, group walk, whole-array read/writesynthesize from primitivesTrivially derived from __getitem__/iterdir; cheap, correct, driver-agnostic.
Chunk I/O, compression, codec encode/decode, sharding indexdelegate to backendThis is precisely what zarr-python / tensorstore / zarrs are for. Reimplementing invites subtle corruption.
A capability a driver simply lacksraise, don't emulateOne named error. Half-built emulation of a codec or shard index is worse than an honest refusal.

Litmus test for "should we own this fallback?": if it can be written purely in terms of members the driver already exposes, synthesize it; if it needs to re-encode bytes or re-implement a compression/sharding format, it belongs to the backend.

07

All-versions metadata & lossless conversion

This is the feature you singled out, and it's the one with the most latent bugs. The model exists (zarr v1/v2/v3, OME v0.1–v0.6) but the conversion paths are largely untested, one is buggy, one is a broken stub, and "lossless" is nowhere defined as a contract.

What's there, and what's wrong with it

  • zarr v2↔v3 conversion exists but is untested, implemented as per-leaf to_version() on codecs, dtypes and filters plus array-level _to_v2/_to_v3. verify
  • v3→v1 looks buggy — the compressor is double-converted and a recomputed dtype is discarded. fix
  • v1→v2/v3 is absent — the v1 array class has no to_version at all. implement
  • OME to_version is a broken stub — it splits __qualname__ expecting a module path that isn't there, targets the wrong subpackage, has no callers and no tests. Rewrite it as explicit per-version migration, not reflection. replace
  • No OME↔zarr-format coupling is encoded. OME v0.1–v0.4 sit on zarr v2; v0.5+ sit on zarr v3 (metadata nested under an ome key). Today that lives only in which submodules happen to exist. Make it an explicit table. add

A conversion contract worth committing to

Parse into a superset that keeps unknowns

The FlexibleMetadata extra_items dict already retains fields the model doesn't name. Lean on it: nothing read is silently dropped, so a field a target version can't express can still be carried.

Convert by explicit field maps, not reflection

One converter per version pair, hand-written where the spec changed shape (axes, transformations, the ome nesting at v0.5). Reflection over class names can't know that multiscales moved.

Make "lossy" a choice, not an accident

A policy flag — strict (raise if a field can't be represented), annotate (stash it in a namespaced extra), or lossy (warn + drop). The per-resolver asymmetry bagof-magic uses is the model: pass a value through, but never invent one.

Prove it with round-trips

Property test: for every version pair the spec allows, a → b → a equals the original. That single family of tests is what turns "as lossless as possible" from an aspiration into a guarantee.

Keep both representations, on purpose

The TypedDict schemas/ and the attrs metadata/ are complementary, not redundant: schemas are a declarative validation surface for raw JSON; metadata is the functional model that converts. Keep them — but add the missing tests (every zarr version, every OME version, and the negative cases that are currently commented out).

The sequence

Seven phases, ordered so each unblocks the next. Phase 0 is non-negotiable and small; the dependency swaps come before the API hardening; the big attrs migration comes only once the model is stable and tested.

0

Unblock & guard blocker

Make the package import again and never break this silently twice.

  • Fix the abc/path.py ↔ _core/path.py name mismatch (or leapfrog straight into Phase 1).
  • Make __init__.py imports lazy / guarded so a missing backend or a WIP module can't take down the whole package.
  • Add CI that actually imports abczarr and runs the suite on Python 3.8 and current — the two ends where things differ.

exit  green suite, package imports on both interpreters.

1

Adopt bagof-paths

Delete _core/path.py; rebuild the store/path layer on bagof-paths.

  • Rewrite abc/path.py + abc/store.py onto bagof-paths' Path/AsyncPath and register_protocol.
  • Point _core/attributes.py and the drivers at the new path type (mostly the vanilla subset).
  • Carry read_only as store state; keep .wrapped for backend-specific needs.

exit  2,375 lines gone; local + one cloud protocol tested end-to-end.

2

Consolidate the abc API

One coherent abstract layer with the contracts from §03–§05.

  • Remove _abc.py; make abc/ the single source of truth.
  • Introduce the surface spec table, the node.native contract, driver.supports(…), and UnsupportedZarrOperation.
  • Settle the sync/async model and add the parity test.

exit  a documented driver contract a new backend can target.

3

Harden metadata & conversion

Turn the untested model into a tested, lossless-by-contract one. core value

  • Fix v3→v1; implement v1→v2/v3; add the strict/annotate/lossy policy.
  • Replace OME to_version with explicit per-version migrations; add the OME↔zarr-format table.
  • Round-trip property tests across every version pair; re-enable the negative validation tests.

exit  every advertised version parses, converts, and round-trips under test.

4

attrs → bagof-magic

Retire _core/auto once its edge cases are proven portable. staged

  • Verify RFC-2119 markers, DType/JSON converters, and TypedDict validation against the bags first.
  • Migrate innermost-first behind shim decorators; delete _core/auto when nothing imports it.
  • Express the version lattice with polymorphic + on={…}.

exit  ~3k lines of home-grown engine replaced; behavior unchanged under the Phase-3 tests.

5

Finish the drivers

Make the multi-backend promise real and measured.

  • Complete zarr-python (fill_value, groups) and test tensorstore against the contract.
  • Implement the zarrita and zarrs drivers on the thin contract from Phase 2.
  • Publish a capability matrix (driver × feature) driven by supports().

exit  the same test suite passes against every installed backend.

6

Docs, polish, release

Make it usable by someone who isn't you.

  • Runnable pycon docstring tests on the 3.8 floor (the bagof house convention).
  • A "lead with what the user writes" guide; the capability matrix; a conversion-fidelity page.
  • Drop the "DO NOT USE YET" once Phases 0–5 hold.

exit  a first tagged release.

09

Open questions to settle first

Four things worth a decision before committing engineering time — each can shift the plan's cost.

Does bagof-paths expose a subclassable store seam?

If Path/AsyncPath can't be subclassed for StorePath, model the store as a wrapper holding a path instead. Settles Phase-1 shape.

Is bagof-magic ready for the DType & RFC-2119 cases?

If not, Phase 4 waits — and that's fine. Don't keep extending _core/auto in the meantime; freeze it.

Which OME versions are in scope for v1?

Full v0.1–v0.6 round-tripping is a large test matrix. A defensible cut: v0.4 & v0.5 lossless, older ones read-only.

Sync-primary or async-primary internals?

This plan recommends sync-primary (numpy/dask consumers). Revisit only if the dominant use case turns out to be high-concurrency cloud I/O.
